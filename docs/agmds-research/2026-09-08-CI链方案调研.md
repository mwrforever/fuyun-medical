## 2. 三套方案对比总表

> 预计时长为 ubuntu-latest 单机并行运行的经验量级估算（非实测）：后端大头为 Maven 多模块 `verify` + Testcontainers 首次拉取 PG16+TimescaleDB/Redis/RabbitMQ 镜像（约 2-5 分钟）；前端为 pnpm 冷缓存安装 + Vite 构建；CodeQL/Trivy 可与主链并行，不计入关键路径的按"（并行）"标注。

| 方案 | job/阶段清单 | 门禁强度 | 预计时长（PR 关键路径） | 维护成本 | 全局规范满足度（硬约束逐条） |
| --- | --- | --- | --- | --- | --- |
| A 基础门禁 | 3 job：backend（mvn verify = 单测+Testcontainers 集成+JaCoCo report）／frontend（pnpm install --frozen-lockfile → lint → type-check → test → build）／images（三镜像构建，main push 才推 GHCR）；push(main)+PR 触发；分支保护 required status checks | 弱：仅"测试不过不得合入"有机器强制；格式/覆盖率/提交规范靠人工 | 约 15-25 分钟 | 低（3 个 workflow 文件级维护） | ①部分（前端 lint 在链上，后端无风格门禁）②部分（全量测试必跑，但 100%/80% 门槛无机器强制）③不满足（无编码/行尾自动校验）④满足（PR 全量测试必过） |
| B 严格门禁（预判推荐） | A 基础上扩为 5 job：backend（spotless:check 硬门禁 + mvn verify + JaCoCo check 硬门槛）／frontend（prettier --check + eslint --max-warnings=0 + vue-tsc + test + build + pnpm audit 门禁）／backend-dependency-audit（OWASP dependency-check）／commit-message（commitlint）／workflow-lint（actionlint + pre-commit run --all-files 同源校验）；本地 pre-commit hooks 与 CI 同命令 | 强：风格/格式/覆盖率/依赖审计/提交规范/workflow 语法全部机器阻断，无法人工绕过 | 约 20-30 分钟 | 中（格式规则初期收敛、覆盖率阈值随模块调整） | ①满足 ②基本满足（覆盖率硬门槛落地，聚合口径受 JaCoCo 已知限制约束，见 §3.2）③满足（pre-commit 官方 hooks + .gitattributes）④满足 |
| C 安全合规增强 | B 的 5 job 全保留；新增（与主链并行）：CodeQL（push/PR + 每周 schedule，java 与 javascript-typescript 双语言）／Trivy（镜像扫描门禁 + fs/secret 扫描，action 按 SHA pin）／dependency-review（PR 依赖变更审查）；另配 Renovate 或 Dependabot 自动升级提案 | 最强：B 全部 + SAST/SCA/容器扫描三层安全门禁 + 供应链事件防护（SHA pin），符合医疗等保对留痕的要求 | 约 25-40 分钟（CodeQL 有缓存后增量约 3-8 分钟） | 中高（安全告警分流、自动升级 PR 审阅量） | ①②③④全部满足，并额外形成安全审计记录（等保友好） |

### 3.4 贯穿性技术事实（Java 17 红线汇总）

本项目 CI 运行时锁定 Temurin 17，由此形成四条工具选型红线（均有官方来源，见 §1）：

1. **格式化器**：google-java-format ≥1.22 需 JDK 21 运行 → Spotless 选 palantir-java-format 或 eclipse JDT；
2. **Checkstyle**：13.x/14.x 需 Java 21 → 锁 12.x，或等未来升级 JDK 后再上 14.x；
3. **Error Prone**：当前版需 JDK 21，JDK 17 只能用停更的 2.42.0 → 本项目不引入；
4. **SonarQube 扫描器**：2026-07 起 Java 17 运行时支持移除 → 若引入需在 CI 为扫描步骤单独安装 JDK 21（setup-java 支持多 JDK），该成本建议向用户明示后再决策。

## 4. 推荐与理由

预判推荐**方案 B「严格门禁」作为上线基线、方案 C 作为第二阶段演进目标**：方案 B 已将全局质量规范四条硬约束全部机器化（lint+格式化+全量测试自动阻断、覆盖率 100%/80% 双阈值、UTF-8/LF 钩子校验、PR 全量测试必过），且工具组合已按 Java 17 红线完成筛选（Spotless+palantir、Checkstyle 12.x、不引入 Error Prone），PR 关键路径仅比方案 A 多约 5 分钟、维护成本可控；方案 C 的 CodeQL/Trivy/dependency-review/自动依赖升级对医疗等保合规有明显价值，但主要收益是安全留痕与供应链防护，可在 backend/web 代码成形、方案 B 稳定运行后再开启，避免起步阶段告警噪音淹没真实门禁信号。
