# P0 工程骨架交付 · 交付loop执行设计

> 本文档为唯一执行依据。执行者必须按阶段门禁（P0→P6）顺序推进，循环仅在满足退出条件后进入下一阶段；**全任务仅在第五章 DoD 全部满足后退出主循环**。凡需用户决策的事项（升级、需确认动作、L3 汇总、决策点 D-2/D-3）一律经 ask_question 阻塞等待用户选择，**用户长时间未响应也必须一直等待**，禁止以任何理由中断执行（终止/放弃/超时自答/替用户默认），拿到决策后完整续跑。根 `AGENTS.md` 与 `backend/AGENTS.md`、`web/AGENTS.md` 为最高约束，产出与之冲突即不合格。

## 0. 执行框架总览

### 0.1 目标

按 PLAN-P0-01 完成其 §1 的 PR-1~PR-5 并依序合入 `dev`；完成判定 = 计划 §3 DoD 全满足且证据落盘。

### 0.2 主控循环（Master Loop）

```text
初始化：通读三级宪法+PLAN-P0-01+定稿 §6 → sdd-workspace 建台账(.superpowers/sdd/) → 冲突扫描(一次问齐)
P0 分支与门禁准备：建 dev 推送+gh api 配保护(镜像 main 五 checks) → G0
P1 PR-1 工程骨架(B1.1→B1.4) → 批次循环 → 全分支终审 → PR 过审合入 dev → G1
P2 PR-2 M20 治理构件(B2.1→B2.3) → 同上 → G2
P3 PR-3 M01 系统与权限(前决策点 D-2;B3.1→B3.4) → 同上 → G3
P4 PR-4 M14 IoT 通路(前决策点 D-3;B4.1→B4.4;T-R3-2 实测锁定) → 同上 → G4
P5 PR-5 收口(B5.1→B5.2) → 同上 → G5
P6 终验：DoD 逐项附证据 → 终验报告 PR 合入 dev → 全满足退出；未满足回退责任阶段(≤3 轮)
批次循环(P1~P5 共用)：
while 存在未完成批次:
    逐任务派实现专员(task-brief 提取；TDD：RED→GREEN→REFACTOR；conventional commits)
    批次毕 → review-package 生成 diff 包 → 派审核专员(spec 符合+代码质量双结论)
    ├─ 通过 → 台账记 complete，下一批 ├─ 不通过 → 修复循环(≤5 轮，见第六章)
    └─ 超限熔断 → 非承重 parked(附理由)/承重 BLOCKED 升级用户
全批次毕 → 全分支终审(最强模型，requesting-code-review 模板) → 修复 → PR→dev
PR 循环：五 checks 绿+/code-review findings(置信≥80) → receiving-code-review 核实→修复→push→复审
    → 无 findings → 合入 dev → 删 feature 分支 → 台账登记
```

## 1. 任务范围定义

### 1.1 范围内（In Scope）

1. T1~T5 = 计划 §1-PR-1~PR-5 全部交付物，明细与验收以计划原文为准（W-3 即 T1）。
2. dev 建管与双分支 CI 门禁（main 已生效，dev 镜像同款）。

### 1.2 范围外（Out of Scope）

1. 计划 §4 全部项；浏览器 E2E 维持排除（端到端口径裁决见 §8）。
2. dev→main 合并（用户裁决：P0 后停留 dev）。
3. 宪法与计划修订（发现缺陷登记 TASK.md 升级用户）。

### 1.3 拆分依据

定项模式：PLAN-P0-01 一份 spec，其 PR-1~PR-5 序列即 T1~T5，不拆分重设计；WBS 批次仅为复审单元（简单 3~5 个/批、复杂 1~3 个/批，用户指令）。

## 2. 全局执行总则

1. **阶段门禁制**：未满足出口门禁禁止进入下一阶段，回退记录进台账。
2. **决策链**：L1 项目内部（宪法/specs/定稿/git）→ L2 外部文档 → L3 用户经 ask_question 一次汇总，不得跳级。
3. **循环收敛**：修复循环设最大迭代，超限升级用户，禁止静默放弃。
4. **单一事实源**：计划与定稿为唯一依据，版本取定稿表，新依赖先在 PR 描述申报；发现规格缺陷先登记升级。
5. **状态续传**：每过一个门禁即更新台账，中断后从台账+git log 恢复；完成声明必附证据。
6. **subagent 执行制**：调研/实现/审核一律派遣，主控仅编排；实现专员严禁并行。

## 3. 阶段详细定义

**步骤**：1. `git switch -c dev origin/main` 并推送 → gh api 验证 dev 存在。2. gh api 配 dev 保护（required_status_checks=main 五项+enforce_admins）→ 两分支查询一致。3. 台账首行 `# SDD ledger — plan: docs/plans/2026-09-08-P0实施计划.md`。4. 冲突扫描。

**出口门禁**：[ ] dev 保护与 main 五 checks 完全一致（gh api 证实）；[ ] 台账已建且首行为计划路径；[ ] 冲突扫描完成（分歧已裁决）。

## 4. 派遣规范（subagent 执行制）

每次派遣六要素：【角色】单一职责；【目标】一句话可验证；【输入】具体路径（task-brief 为需求唯一来源）；【职责】边界；【输出】路径+结构（报告含 DONE/DONE_WITH_CONCERNS/NEEDS_CONTEXT/BLOCKED、commits、测试摘要）；【完成标准】可验证。并行规则：实现专员严禁并行；不同 PR 严禁并行；只读调研/审核可并行。

## 5. 完成条件（Definition of Done）

- [ ] compose 七服务全 healthy；`--profile sim` 端到端演示通过（IoTDA→AMQP→TimescaleDB→WebSocket），或 IOTDA_* 缺失按计划延后登记
- [ ] 后端门禁绿含 JaCoCo 双阈值（核心包 1.00）；前端五门禁绿（本地输出+CI 日志）
- [ ] 五个 PR 均经 /code-review 审核通过后合入 dev
- [ ] main 与 dev 保护均含五 required checks（gh api 输出落终验报告）
- [ ] CF-1/CF-2/CF-7 冻结登记 event_registry（迁移+测试断言）
- [ ] TASK.md W-3 销项、T-R3-2/3 回填
- [ ] 台账完整；终验报告每项附证据并合入 dev；本地最终停留 dev

## 6. 循环与中止机制汇总

| 循环 | 触发条件 | 动作 | 退出条件 | 最大迭代 | 超限处理 |
| --- | --- | --- | --- | --- | --- |
| 批内修复循环 | 审核不通过或 Critical/Important | 1-3 轮续原专员、4-5 轮更强模型新专员修复+覆盖测试重跑+scoped 复审 | 双结论通过或熔断裁决完 | 5 | 熔断：非承重 parked；承重升级用户 |
| PR 审核循环 | checks 红或 findings | 核实→修复→push→复审 | checks 绿且无 findings | 5 | 升级用户（附 findings） |
| 终验循环 | DoD 未全满足 | 回退责任阶段重走 | DoD 全勾 | 3 | 升级用户 |

**中止条件**：删过审 feature 分支、合并过审 PR 不另确认；循环超限、D-2/D-3、计划/宪法冲突经 ask_question 阻塞等待；IOTDA_* 缺失不阻塞；禁止静默放弃或伪造证据。

## 7. 红线禁止事项

1. 禁止跳过门禁或出口条件未满足即推进阶段
2. 禁止未经测试验证即标记完成；禁止无失败测试先写生产代码（TDD 铁律）
3. 禁止偏离计划与定稿实现；发现缺陷先登记升级
4. 禁止绕过批次审核、终审或 /code-review 直接合入
5. 禁止缩范围、削减交付物或边界测试换「完成」
6. 禁止伪造/跳过/选择性跑测试与 CI；禁止绕过 PR 直推 main/dev
7. 禁止 L1/L2 可调研时直接问用户
8. 禁止重做台账记 complete 的任务；禁止主控亲自实现或修 findings
9. 禁止产物不落盘不提交
10. 禁止等待用户决策时中断执行，必须 ask_question 阻塞等待至决策
