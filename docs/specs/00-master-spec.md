## 1. 项目定位与范围边界

### 1.1 系统定位

面向院级（二级~三级医院，按 1000 床位规模设计基线）的大型医疗管理系统，覆盖"智慧服务—智慧医疗—智慧管理"三位一体（国家卫健委智慧医院框架），并以**医疗设备物联网接入（对接华为云 IoTDA）**作为核心差异化能力。

### 1.2 技术基座（既定约束）

- 后端：Java 17 + Spring Boot 3（模块化单体，Maven 多模块）
- 数据库：PostgreSQL 16（业务库）+ TimescaleDB（设备遥测时序库）+ Redis（缓存/会话）
- 前端：Vue 3 + TypeScript + Element Plus（管理端/医护工作站）、ECharts（大屏）、WebSocket（实时推送）
- 物联网：华为云 IoTDA（设备接入）+ 华为云 AMQP 转发订阅
- 消息中间件：RabbitMQ（决策依据见 4.3 章）

### 1.3 范围边界（本期不做，列为预留扩展）

| 不在本期范围 | 说明 |
| --- | --- |
| 区域卫生信息平台 | 与省市健康档案平台对接仅保留上报接口位（M20） |
| 科研大数据平台/CDR 全量 | 保留临床数据仓库接口位，不本期建设 |
| 医学 AI 辅助诊断（大模型） | 预留模型服务接入点（如病历质控、辅诊建议），本期不建 |
| PACS 高级三维后处理/AI 影像 | 本期实现影像归档/浏览/报告主干，三维后处理建议集成 DCM4CHEE 或商用组件 |
| 医院财务/HRP 全量 | 仅做收费、对账与物资/设备管理，总账对接财务系统 |

## 2. 调研依据（真实生产实践来源）

本 spec 的功能清单不是凭空设计，以下关键事实来自公开的真实生产系统、行业标准与论文（完整来源清单见第 12 章）：

### 2.1 功能完整度标尺：智慧医院评级体系

- 国家卫健委《电子病历系统应用水平分级评价管理办法（试行）》：要求二级以上医院参评，2019 年所有三级医院须达 3 级以上、2020 年达 4 级以上；评价分 0-8 级，4 级要求"全院信息共享、具备医疗业务闭环"，5 级要求"统一数据管理、高级临床决策支持"。→ 决定本系统必须具备**医嘱、输液、检验/检查危急值、输血等闭环管理**与**全院级数据共享**。（来源：qmjksjzx.com/news_view.aspx?id=358；CSDN 电子病历 4 级解读 blog.csdn.net/oldfellow8312/article/details/134624921）
- 国家医保局编码贯标：医保信息业务编码已由 15 项扩展到 **22 项**（药品、耗材、诊疗项目、疾病诊断和手术操作、医保结算清单等），定点机构须使用国家基线版医保接口结算。→ 收费/医保模块必须内建国家编码对照与基线接口。（来源：code.nhsa.gov.cn；nhsa.gov.cn/art/2024/11/29/art_14_14901.html）
- DRG/DIP 支付改革：病案首页数据质量与编码规范是分组付费的"生命线"，要求系统具备病案首页质控、结算清单生成、费用监测能力。（来源：nhsa.gov.cn/art/2021/11/26/art_104_7413.html）
- 等保 2.0 三级：三级系统每年测评一次、75 分以上达标，涵盖安全审计、访问控制、加密等近 300 项要求。→ 决定审计日志、权限、加密等非功能需求。（来源：ahdjbh.com/dengbaoceping/734.html）

### 2.2 主流厂商产品体系（模块划分参考）

- 卫宁健康 WiNEX 采用"1+X"战略：1 个数字基座（中台）+ X 个场景产品，覆盖**智慧服务（面向患者）、智慧临床（面向医护）、智慧管理（面向运营）**三大产品族，智慧医院全系产品 180 余个。→ 本 spec 按同思路划分业务域。（来源：chima.org.cn/Html/News/Articles/4592.html；support.huaweicloud.com/wsmcs-health/wsmcs_01.html）

### 2.3 医疗设备物联网真实生产案例（重点）

- **解放军总医院第一医学中心 ICU 医疗设备物联网**（已稳定运行 25 个月的真实生产论文，PMC11955343）：
  - 设备接入三种模式：**物联网网关模式**（一台工作站连接全病区设备，效率高但单点风险）、**串口服务器模式**（每床串口采集盒，RS232/485 转 TCP，服务器端解析）、**边缘适配器模式**（每台设备绑定一个树莓派类适配器，去中心化、抗服务器宕机）；
  - 协议：基于 IHE-PCD 框架，体征/波形用 HL7 ORU^R01（PCD-01），报警用 ORU^R40（PCD-04），消息经 **AMQP** 上传，术语用 Rosetta 映射（如心率 MDC_ECG_HEART_RATE）；
  - 实测数据量：4 个 ICU 日均 15,531 MB；25 个月累计 217.6 亿条 / 12.5 TB，其中**波形数据占 86.64%、体征数据占 7.92%、报警数据占 5.44%**；
  - 应用效果：护理集成系统自动将生理数据导入护理记录，**每天减少护士 0.8 小时/床**工作量；多数**输液泵没有数据通信接口，暂无法直接物联**（需外置传感器）。
- 华为《临床医疗物联网解决方案》：医疗设备"剪辫子"（有线转无线），通过串口代理将 IP 报文转串口数据，适配存量串口设备。（来源：support.huawei.com EDOC1100286429）
- EMQ 医疗物联网方案：以 MQTT 为核心连接输液泵、呼吸机、实验室设备，形成统一患者护理视图。（来源：emqx.com/zh/solutions/healthcare-and-life-sciences）
- 苏大附一院三甲物联选型实录：产品线包括可视化边缘物联网关、多核定位引擎、智慧病房交互终端、智能输液监测、婴儿防盗、医疗资产管理、医废溯源。（来源：100ec.cn/brand/2686657.html）

### 2.4 智慧病房子系统清单（生产方案）

病房门口屏、智能门禁（护士手环联动）、生命体征采集一体机（二维码匹配患者身份、实时上传、可共享至护理记录单）、智能输液监控（剩余量 15/10/5 ml 逐级报警、语音提示）、病区呼叫对讲（多屏联动+穿戴接收）、智能考勤、护士手环（身份/门禁/定位/消息）。（来源：cnblogs.com/kymdidicom/p/14305787.html；联新 lachesis-mh.cn）

### 2.5 华为云 IoTDA 平台能力（官方文档）

- 数据转发方式矩阵：AMQP、MQTT 推送、HTTP/HTTPS 推送、DMS Kafka、RocketMQ、DIS、LTS、FunctionGraph、OBS、GeminiDB Influx、RDS MySQL、RDS PostgreSQL（仅企业版直转）。规则引擎支持 SQL 过滤，数据来源含设备属性/设备消息/设备状态/设备异步命令状态等。
- **关键约束**：公网转发流量限制 1 MB/s（超出直接丢弃，企业版内网无限制）；AMQP 订阅服务端**仅保存 24 小时以内且小于 1GB 的积压数据**，超时清理（→ 自建后端消费必须高可用、快速落库，且告警类关键消息需冗余通道兜底）；AMQP 推荐 TLS 1.3、自动确认，中断未确认数据重连后重推。
- 设备侧：物模型（服务/属性/命令/事件）、MQTT/TLS、一机一密/一型一密、设备影子、联动规则、命令下发（同步/异步）、网关与子设备（Modbus/OPC-UA 泛化接入）、OTA。（来源：support.huaweicloud.com/usermanual-iothub/iot_01_0024.html、iot_01_0003.html）

### 2.6 临床医技系统生产实践要点

- LIS：条码管理、标本全程时间管理、**检验仪器双向通讯（ASTM E1394 / HL7）**、设备数据采集、质控（Westgard）、危急值管理。（来源：dayuansoft.cn Smart.LIS；chisc.net/doc/view/2055.html）
- 手麻：自动采集监护仪/麻醉机/血气分析仪数据生成电子麻醉记录单（5 分钟粒度），有国家卫健委《麻醉记录单标准》行业标准约束。（来源：nhc.gov.cn 麻醉记录单标准 PDF；todaymedtech.com）
- 移动护理 PDA：闭环环节按"收药—摆药—核对—执行—拔针"五环节扫码管理；真实医院 PDA 含护理录入、医嘱执行、标本采集、巡视等 21 个模块；移动护理已被纳入电子病历评级标准。（来源：zbcg.301hospital.com.cn 招标技术需求；hyrmyy.com；cn-witmed.com/list/36/21683.html）
- PACS/RIS：登记→检查→影像接收（DICOM）→阅片→结构化报告→归档全流程，遵循 DICOM/HL7/IHE 标准。（来源：developer.aliyun.com/article/1757538；wedcm.com/artical83.htm）

### 2.7 消息中间件选型行业共识

- Kafka：高吞吐数据管道，适合日志/流处理；RocketMQ：金融级、事务/顺序/延迟消息；RabbitMQ：灵活路由、轻量级事务、低运维成本。（来源：juejin.cn/post/7491607061782233151；cnblogs.com/shiyuelp/p/19384355）
- 物联网场景关注低延迟与协议支持，MQTT 面向设备侧、传统 MQ 面向后端应用侧，两者是互补关系而非替代关系。（来源：help.aliyun.com/zh/apsaramq-for-mqtt/application-scenario-comparison-of-mqtt-and-rocketmq）

## 4. 技术架构决策

### 4.1 总体分层架构

```
终端层    医生站/护士站 PC | PDA | 床旁屏/门口屏 | 大屏 | 患者手机 | 自助机
接入层    Nginx(HTTPS/WSS) | WebSocket 推送服务 | API 网关（鉴权/限流）
应用层    模块化单体（M01-M20，Maven 多模块，模块间仅经接口/事件交互）
消息层    RabbitMQ（领域事件总线/告警分发/延迟消息） ← 华为云 IoTDA AMQP 订阅（设备数据直连 iot 模块消费）
数据层    PostgreSQL 16（业务库，Flyway 管理） | TimescaleDB（遥测超表） | Redis | MinIO/对象存储（影像/文件）
外部      华为云 IoTDA（设备接入/物模型/命令/联动） | 医保接口 | CA 电子签名 | 短信/公众号
```

### 4.2 架构形态：模块化单体（而非微服务）

- 真实生产实践：多数医院级 HIS 仍以一体化架构+模块化设计为主流，微服务拆分多见于互联网医院/平台型产品；单体模块化可保证 HIS 强事务（医嘱-计费-库存联动）一致性，避免分布式事务复杂度。
- 规模判断：1000 床位医院单院区部署，单体（读写分离 + 关键模块可独立进程化）足够；预留模块边界清晰，未来可按模块拆微服务。

### 4.3 消息中间件决策（回答"是否需要引入 MQ、引入哪个"）

**结论：引入 RabbitMQ（3.13+，quorum queue 队列）。**

引入依据（每个场景都有真实生产对应）：

| 场景 | 说明 | 为什么需要 MQ |
| --- | --- | --- |
| 跨模块领域事件 | 医嘱开立→药事审核→发药→护士执行；检验/检查申请→报告→危急值通知 | 医院核心是"闭环"，闭环=异步事件链；同步调用会造成模块强耦合与级联失败 |
| 告警分发 | IoT 设备告警（输液告急/离床/冷链超标）→ 护士站大屏 + PDA + 手环 + 短信多端扇出 | 一事件多订阅方，fanout/路由天然匹配 |
| 延迟/超时提醒 | 医嘱超时未执行、检验标本超时未送检、会诊超时响应（评级闭环要求） | TTL + 死信交换机实现延迟消息 |
| 流量削峰 | 门诊高峰挂号收费、批量体征采集上传 | 保护数据库与下游 |
| 可靠投递 | 收费/结算类异步任务（医保对账、发票） | 持久化 + 确认 + 重试 |

**为什么不是 Kafka**：本系统设备遥测不经过 RabbitMQ/Kafka 中转（见 4.5），业务事件吞吐属中等规模（百级/秒峰值），Kafka 的分区吞吐优势用不上，反而增加运维与消费语义复杂度。**演进路径**：若未来设备规模过万或需流式分析，可用华为云 DMS Kafka 作为 IoTDA 转发目标（IoTDA 原生支持）做遥测旁路，不影响本决策。

**为什么不是 RocketMQ**：延迟消息/事务消息能力与 RabbitMQ（TTL+DLX/发送确认）在本规模下等价，RocketMQ 运维组件更重；华为云 DMS 提供 RocketMQ 仅作为托管备选项记录。

**与 IoTDA 的关系**：IoTDA 设备数据通过其官方 **AMQP 订阅**直连 `iot` 模块消费（第一跳不经 RabbitMQ），消费后：遥测写 TimescaleDB、业务事件（告警/联动/状态变更）发布到 RabbitMQ 供各模块订阅。理由：原始遥测吞吐高（真实 ICU 单病区可达数百 MB/天，波形 1-500Hz），直接入库更可控，避免 MQ 中转放大消息量与积压风险（IoTDA AMQP 仅缓存 24h/1GB）。

### 4.4 数据存储决策

| 存储 | 用途 | 关键策略 |
| --- | --- | --- |
| PostgreSQL 16 | 全部业务数据（单库多 schema 按 Maven 模块划分） | Flyway 版本化迁移；金额用 NUMERIC(18,2)；审计字段统一 |
| TimescaleDB（PG 扩展） | 设备遥测超表 `iot_telemetry`（按天分区） | 压缩策略（7 天后）、保留策略（明细 90 天/降采样 1 年，可配置）；波形数据默认不落库或边缘降采样，仅体征/报警/事件级数据入库 |
| Redis | 会话、字典缓存、号源/床位并发锁、大屏实时快照 | — |
| MinIO（或华为云 OBS） | 影像文件、报告 PDF、体检报告、设备文档 | 生命周期分层（在线 90 天 → 近线 → 归档） |

### 4.5 设备数据链路（详见第 5 章）

### 5.2 边缘侧接入三种模式（真实生产验证，按病区规模选型）

| 模式 | 做法 | 适用 | 风险 |
| --- | --- | --- | --- |
| A 直连 | 设备原生 MQTT/WiFi 直连 IoTDA（一机一密） | 智能床垫、冷链、输液传感器、环境传感器等物联网原生设备 | — |
| B 串口服务器 | 每床串口采集盒 RS232/485→TCP，帧头帧尾识别后在服务端解析，转 MQTT 上云 | 监护仪/呼吸机等串口私有协议设备（ICU/神外等集中病区） | 服务端解析压力集中，需集群化 |
| C 边缘适配器 | 每台设备绑定一个边缘适配器（树莓派类），解析封装在边缘完成 | 设备分散、要求抗服务端宕机的场景 | 边缘运维数量多 |
| D HL7 引擎 | 支持 HL7 MLLP 的设备/中央站（如迈瑞中央站）→ 集成引擎（M20）→ 平台 | 有 HL7 能力的中高端设备 | 依赖设备型号 |

注：迈瑞等品牌"中央站 + 采集网关"属模式 C 的集中式变体（网关模式），单点故障会导致全病区掉线，实施时须双网关热备。老设备无任何接口的（论文实证：多数输液泵）只能外置传感器或仅做资产化扫码管理（M15）。

### 5.3 华为云 IoTDA 集成设计要点

1. **产品/物模型**：按设备类型建 IoTDA 产品（如 `med-monitor`、`med-infusion`），物模型服务分 `vital`（体征属性）、`alarm`（报警事件）、`control`（命令，如远程调参）；属性命名对齐 Rosetta/MDC 语义（如心率 `MDC_ECG_HEART_RATE`），保证跨品牌归一。
2. **设备接入**：MQTT + TLS，一机一密；网关/子设备拓扑用于模式 B/C 的边缘网关（网关代子设备上下线）。
3. **数据上行**：IoTDA 规则引擎（SQL 过滤资源空间+产品+属性）→ **AMQP 订阅**；`iot` 模块内嵌 AMQP 消费者（Qpid JMS，TLS 1.2/1.3，关键队列客户端确认+幂等消费，断线重连重推）。**必须应对 24h/1GB 积压上限**：消费者无状态可水平扩展、落库批量化；关键告警类消息另配 IoTDA 联动规则 → HTTP 推送平台兜底通道（双通道防丢）。
4. **命令下行**：远程调参/开关走 IoTDA 异步命令；平台侧强制"二次确认 + 权限 + 全程审计"（医疗设备远程控制属高风险操作）。
5. **设备影子**：设备离线时读影子取最后状态；护理/大屏展示"最后上报时间"。
6. **版本选型**：IoTDA 标准版起步（支持规则 SQL 与 AMQP/Kafka 转发即可，无需企业版直转 RDS PG 的能力）；注意公网转发 1 MB/s 限制，如院内带宽紧张评估企业版内网。

### 5.4 数据量估算（基线：1000 床位，按论文实测外推）

- 体征类遥测：假设 3000 台在网设备 × 平均 1 点/分钟 ≈ 50 msg/s 常态，峰值 500 msg/s（全院体征集中采集时段）——TimescaleDB 轻松承载。
- 波形类：真实 ICU 单病区可达 458~10,231 MB/天（取决于设备与采样率），**默认边缘降采样/不落库**，仅麻醉/抢救等场景按需开启波形存储并单独配额。
- 事件/告警：占比约 5%（论文实测 5.44%），走 PG 业务表 + RabbitMQ。

## 10. 关键决策记录与风险

| # | 决策 | 依据 | 风险与对策 |
| --- | --- | --- | --- |
| D1 | 引入 RabbitMQ 作为唯一自建 MQ | 4.3 场景论证；遥测不走 MQ | 中等规模下容量充足；事件风暴风险由 M20 事件治理约束 |
| D2 | 遥测直连 IoTDA AMQP 入 TimescaleDB，不经 MQ | 论文实测数据量（波形占比 86%）+ IoTDA 积压限制 | AMQP 积压 24h/1GB → 消费高可用 + 告警双通道兜底（5.3-3） |
| D3 | 波形数据默认边缘降采样/不落库 | 波形占 12.5TB 中的 86.64%，存储与带宽成本高 | 抢救/麻醉场景按需开启并配额；策略可配置 |
| D4 | 模块化单体 + 严格模块边界 | 强事务一致性（医嘱-计费-库存）；医院单院区规模 | 红线：禁止跨模块读表/直接依赖，仅经服务接口与事件 |
| D5 | 金额、收费、结算全部服务端计算 | 医保结算与审计合规 | 客户端仅做展示；对账模块兜底 |
| D6 | PACS 主干自建 + 高级后处理集成外部 | DICOM 归档/报告为标准组件能力 | 若集成 DCM4CHEE，作为独立子系统经 M20 集成 |
| D7 | 输液泵等无通信接口设备外置传感器接入 | 论文实证多数输液泵无数据接口 | 传感器选型需与临床科室验证贴装可靠性 |
| D8 | 设备远程控制命令强制二次确认+审计 | 医疗设备安全（患者直接关联） | 命令白名单（默认仅允许非治疗性参数查询/设置） |
