## 1. 模块定位与边界

**职责**：为全系统提供组织机构、用户账号、RBAC 功能权限+数据权限、医师执业授权（处方权/麻醉权/抗菌药分级）、国家标准与院内字典、系统参数、统一操作审计、消息通知通道、打印模板。是唯一允许其他所有模块依赖的底座模块。

**非职责**：业务权限的业务规则（如"医嘱审核只能由药师执行"的业务动作校验归 M06/M04，M01 只提供"该用户是否有某功能权限"的原子判定）；CA 证书签发本身（仅对接外部 CA 服务）；患者身份（归 M02）。

**模块红线**：本模块不得反向依赖任何业务模块；审计日志写入必须与业务事务解耦（失败不阻断业务，但必须告警）。

## 2. 调研依据

1. 医疗系统权限设计的行业实践：RBAC 基础模型（用户-角色-权限）之上，医疗场景必须叠加**科室/病区维度的数据权限**（同一角色在不同病区可见数据不同），几乎所有医疗系统都采用"功能权限 × 数据范围"二维模型。（来源：cloud.tencent.com/developer/article/2311243《医疗系统的权限就该这样设计》；javaguide.cn 权限系统设计）
2. 等保三级要求：身份鉴别（口令复杂度/失败锁定）、访问控制（最小授权、默认拒绝）、安全审计（覆盖每个用户、留存≥6 个月、受保护不可删改）。（来源：ahdjbh.com 等保 2.0 解读；百度百科等保三级认证条目）
3. 医院主数据实践：巴彦淖尔市医院将字典分为财务/机构/药品/手术/其他五大类集中管理，由平台统一分发解决系统间数据一致性。（来源：chima.org.cn/Html/News/Articles/6196.html）
4. 医疗数据分级：病历等核心数据仅限诊疗关系内的授权人员查看，敏感度分级访问。（来源：fanruan.com 医疗数据权限管理）

## 3. 方案推导（关键设计点选型）

### 3.1 权限模型：RBAC0 vs RBAC1（角色层级）vs RBAC+数据范围

| 方案 | 说明 | 评估 |
| --- | --- | --- |
| RBAC0 | 用户-角色-权限三层 | 无法表达"同角色不同病区数据可见性"，医疗场景不够 |
| RBAC1 | 角色继承层级 | 医院角色数量可控（<100），层级带来的隐式继承反而使授权审计困难 |
| **RBAC0 + 数据范围（选定）** | 功能权限走角色；数据可见性由"角色×数据范围类型（全院/院区/科室/病区/本人）"二维授予，授权主体可直接绑定科室/病区集合 | 匹配医院"按病区排班执业"的真实形态；审计清晰（谁在哪个范围有什么权限可全量导出） |

选定：RBAC0 + 数据范围。临床授权类权限（处方权、麻醉药品处方权、抗菌药物分级权限）**不进角色体系**，独立建"执业授权"实体——因其有法定有效期、审批与吊销语义，与功能角色生命周期不同（调研依据 1、4）。

### 3.2 字典管理：直接更新 vs 版本化生效

直接更新简单，但收费/医保场景需要"结算时点字典快照"（费用发生后字典调价，历史费用仍需按当时价格与编码再现），且等保审计要求变更可追溯。**选定版本化**：字典类型下建版本，版本有草稿/发布/废止状态与生效时间；业务表存 `dict_code + version`（或结算时冗余快照字段）；发布产生广播事件供各模块刷新缓存。

### 3.3 审计落点：应用切面 vs 数据库审计

数据库审计（触发器/日志）能捕获绕过应用的变更但无法记录业务语义（"为什么改"）；应用切面可携带操作者、业务单据号、终端信息。**选定应用统一审计切面为主**（注解声明 + 异步批量落库 + 独立 schema 只增不改），数据库层凭据隔离（应用账号对审计表无 UPDATE/DELETE 权限）作为等保"不可篡改"要求的兜底。

## 4. 领域模型

| 实体 | 关键字段 | 说明 |
| --- | --- | --- |
| 组织 org | org_type(院区/科室/病区/班组)、parent_id、org_attr(临床/医技/职能)、sort | 树形；病区必须挂科室下 |
| 用户 user | login_name、密码散列、user_type(员工/系统/接口)、status、失败计数、锁定至 | 系统账号用于模块间调用，接口账号用于外部对接 |
| 员工 employee | user_id、姓名、工号、职称、执业证书号、org 归属（可多） | 1:1 用户（员工类型） |
| 角色 role | role_code、role_name、data_scope_type(ALL/HOSP/DEPT/WARD/SELF) | RBAC0 |
| 角色授权 | role_menu、role_api、role_org(角色×具体科室/病区集合) | 数据范围=WARD/DEPT 时必须配置 org 集合 |
| 执业授权 practice_grant | employee_id、grant_type(处方权/麻精处方权/抗菌药{非限制/限制/特殊}/手术分级)、legal_basis、valid_from/valid_to、status(生效/停权/过期)、审批引用 | 医师执业与处方权管理（FU-M01-04）；唯一权威源，业务模块经 API 校验 |
| 字典 dict_type / dict_version / dict_item | type_code、version、status(草稿/发布/废止)、item_code/item_name/parent_code/扩展属性(JSONB) | 国家标准字典（ICD-10、医保 22 项等）与院内字典（费别/频次/途径）同构管理 |
| 系统参数 sys_param | module、param_key、param_value、env | 分模块命名空间 |
| 审计日志 audit_log | 操作者、动作类型(登录/写/打印/敏感查询)、资源、业务单据号、终端 IP、traceId、结果、occurred_at | 只增表；独立数据库账号写入 |
| 通知通道 notify_channel / 通知任务 notify_task | channel_type(站内/短信/公众号/钉钉企微)、receiver、template、payload、status、retry | 供各模块发送（发送本身异步） |
| 打印模板 print_template | biz_type(腕带/条码/票据/文书)、template、版本 | 套打定位配置 |

## 5. 状态机与业务流程

- **user**：`ACTIVE → LOCKED(连续失败≥5 次，自动 30min) → ACTIVE`；`ACTIVE ⇄ DISABLED`（停用保留数据）。
- **dict_version**：`DRAFT → PUBLISHED(生效时间到达或立即) → DEPRECATED`；同一 type 同一时刻仅一个 PUBLISHED；发布动作发 `system.dict.published` 广播事件。
- **practice_grant**：`EFFECTIVE → SUSPENDED(吊销/停权) `；`EFFECTIVE → EXPIRED(到期自动)`；授权变更全程留痕并广播 `system.practice.changed`（药事/手麻订阅）。
- **notify_task**：`PENDING → SENDING → SENT / FAILED(重试 N 次后)`；FAILED 进死信人工处理。
- 主流程（登录鉴权）：登录 → 颁发访问令牌（含 userId/org 范围/角色摘要，短时效）→ 网关/服务侧鉴权（API 权限 + 数据范围注入查询上下文）→ 审计切面记录。

## 6. 功能实现设计（逐 FU）

| FU | 优先级 | 实现设计要点 |
| --- | --- | --- |
| FU-M01-01 组织机构 | P0 | 树形闭包表 + 邻接表双写（查询快、移动子树准）；停用组织需无在职员工与在用床位——经本模块定义的“组织停用前置校验”SPI 扩展点校验，M04 注册床位占用查询实现（依赖倒置，见第 8 节） |
| FU-M01-02 用户员工 | P0 | 密码策略（长度≥8、复杂度、90 天更换、历史 5 次不重复）对齐等保；会话管理支持踢出（改密/停用即失效令牌） |
| FU-M01-03 RBAC | P0 | 功能权限点在模块 Spec 的 API 清单中声明（权限点编码 = API 路径），M01 只维护授权关系；数据范围在服务层以查询上下文对象注入（强制拦截器，杜绝漏拼条件） |
| FU-M01-04 执业授权 | P0 | 提供 `POST /api/v1/system/practice/check`（员工+授权类型+时点 → 是否有效）供处方/医嘱/手术开立时强校验；到期前 30 天通知本人与医务；抗菌药权限对齐三级分级 |
| FU-M01-05 电子签名 | P1 | 对接外部 CA/时间戳服务（配置化供应商适配器），签署原文摘要+时间戳存证；病历签名在 M09 调用 |
| FU-M01-06 字典 | P0 | 国家字典初始化数据包（ICD-10/ICD-9-CM-3、医保 22 项、LOINC 子集）随 Flyway 基线装载；字典条目带 `national_standard` 标记不可改 code；映射表（院内码↔国标码）独立实体 |
| FU-M01-07 参数 | P0 | 参数变更发 `system.param.changed`（带 module），相关模块热刷新；敏感参数（密钥类）不入库，走环境变量 |
| FU-M01-08 审计 | P0 | 注解式声明审计点 + 异步批量写；检索界面按人/时间/资源/单据号查询，导出需审批；留存 ≥3 年（高于等保 6 个月底线） |
| FU-M01-09 通知 | P0 | 统一 `POST /system/notify`（业务方给业务标识+模板+参数，M01 负责渠道路由、频控、重试）；发送记录含业务单据号供追溯 |
| FU-M01-10 打印 | P0 | 模板引擎选型：前端渲染（Vue 组件模板）为主，条码/腕带用前端专用组件；票据套打提供偏移量校准配置。范围划分：报表模板归 M19 统计报表域，本模块仅管打印类模板（腕带/条码/票据/文书） |
| FU-M01-11 工作台 | P1 | 工作台=角色×布局配置（卡片/快捷入口），各模块注册“工作台卡片”元数据，M01 只做装配 |

## 7. 对外接口

**REST（节选）**：
- `POST /api/v1/system/auth/login|logout|refresh`
- `GET/POST/PUT /api/v1/system/orgs|users|roles|grants`（管理端 CRUD）
- `POST /api/v1/system/practice/check`（业务校验，被 M03/M04/M06/M10 高频调用）
- `GET /api/v1/system/dicts/{type}?version=`（业务读字典，带缓存头）
- `POST /api/v1/system/notify`、`GET /api/v1/system/audit-logs`、`GET /api/v1/system/params`
- `GET /api/v1/system/mdm/snapshot?topic=`（主数据全量初始化与版本对账接口：按主题返回全量快照与当前版本，供 M20 新模块上线回源与每日版本对账）

**MQ 事件**：
- 发布：`system.dict.published`、`system.param.changed`、`system.practice.changed`、`system.org.changed`、`system.user.changed`
- 订阅：无（根模块）
- 登记义务：上述发布事件须先在 M20 event_registry 登记（生产者/载荷说明/订阅方），后方可发布。

**WebSocket**：站内信通道 `/ws/notify/{userId}`（M01 提供，各业务消息经 notify_task 投递）。

## 8. 集成点

- 被依赖（全模块）：鉴权令牌校验、权限判定、字典读取、组织树、通知发送、审计。
- 字典与组织变更经 `fy.topic` 广播，各模块订阅刷新本地缓存（订阅关系在各模块 Spec 中声明，统一审查时对照）。
- 电子签名：外部 CA 服务适配器（供应商可配置）。
- **组织停用前置校验 SPI（唯一合法反向形态）**：本模块定义“组织停用前置校验”SPI 扩展点接口，M04 注册“床位占用查询”实现并在运行时装配；依赖倒置——接口归本模块所有，运行时回调 M04 实现，本模块编译期不依赖 M04；除该 SPI 扩展点外，不存在任何业务模块反向介入本模块校验的形态。

## 9. 非功能与安全

- 登录接口限流（防爆破）；令牌短时效+刷新机制；全接口默认拒绝、显式授权。
- 密码散列用强慢哈希（bcrypt/argon2 级别）；敏感字段（执业证书号）存储加密。
- 审计表独立账号写入、无更新删除权限；审计查询本身也留痕。
- 性能：鉴权判定走本地缓存（权限变更事件触发失效），P99 < 5ms；字典读缓存命中率 > 99%。

## 10. 测试要点

- 正常：登录→按角色出菜单→数据范围过滤正确（三种范围类型各一例）。
- 边界：权限变更后令牌即时失效；字典新旧版本并行期结算取正确版本；执业授权到期当日 23:59 与次日 00:00 边界。
- 异常：审计写入失败不阻断业务但有告警；通知渠道不可用时任务转 FAILED 且可重推；连续失败锁定与自动解锁。
- 安全：越权访问（横向：他人数据；纵向：无权限 API）全部 403 且留审计。
