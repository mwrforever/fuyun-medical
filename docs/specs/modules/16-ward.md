## 1. 模块定位与边界

**职责**：本模块是智慧病房场景的业务应用层与病房专用硬件的编排层，十一项职责：① 智能输液监控——病区级输液看板与逐级告警的播报编排、输液告急的系统级呼叫联动；② 生命体征自动采集——体征一体机/智能床垫在病区的采集工作流编排与监测视图（权威落卡在 M05）；③ 病区呼叫对讲——呼叫域唯一业务权威：呼叫状态机、多端路由、应答/转接/升级、呼叫→护理任务转换配置；④ 床旁交互屏——患者绑定床位后的内容聚合（费用/报告/宣教/订餐/呼叫/评价）与终端管理、离院解绑；⑤ 电子床头卡/门口屏——床位卡与门口屏信息同步与自动刷新；⑥ 婴儿防盗——标签绑定、布防/撤防状态机、出口告警多端联动与门禁闭锁；⑦ 冷链监控——冷链合规台账（设备档案、温度曲线存证、人工巡检、告警处置与偏差评估记录）；⑧ 人员资产定位 RTLS——标签档案、位置缓存与电子围栏应用（资产防丢调配/防走失/手环定位）；⑨ 环境监测——病区环境快照视图与阈值配置向导（告警判定复用 M14）；⑩ 智能门禁——门禁点/授权策略/通行台账/远程开门与婴儿防盗告警联动闭锁；⑪ 医废溯源——称重、扫码交接、转运接收的全流程台账与统计。

**非职责**：设备接入、物模型、遥测管道、告警判定与告警闭环引擎、设备-患者绑定判定（全部归 M14，本模块只消费其事件与查询接口、配置联动规则）；护理任务的执行权威、护理文书、体征三源仲裁与体温单落卡、护士站大屏护理域聚合（归 M05）；医嘱开立与膳食医嘱权威（归 M04）；报告书写与发布（归 M07/M08，本模块只做已发布报告的展示聚合）；计价、收退费、押金与支付资金动作（归 M13，床旁订餐/自助缴费只做入口与台账）；药品/血液库存权威（归 M06/M12，冷链台账只存"设备内存放物品摘要"供应急转移处置）；资产台账与计量检定（归 M15）；视频监控与录像管理（外部平台，仅预留联动接口位）；主数据与字典（归 M01）。

**模块红线**：
1. 本模块不做任何设备接入与告警判定：感知型设备（输液传感器、一体机、床垫、冷链探头、标签、呼叫按钮、门磁、称重终端、环境探头）的数据与事件一律经 M14 管道与事件获取；阈值/规则判定一律配置在 M14 告警引擎；本模块对设备事件的消费只做场景化业务编排（呼叫链、播报、台账、布防、门禁联动）。
2. 呼叫域业务权威唯一在本模块：呼叫状态机、路由与转接规则、超时升级、呼叫→护理任务转换配置只在本模块；M05 对呼叫仅做大屏聚合展示（其 Spec 非职责声明），任何模块不得自行维护呼叫状态。
3. 床旁屏/床头卡涉及患者隐私数据，一律经本模块服务端聚合 API 输出（终端不得直连其他业务模块），输出过 M02 脱敏规则；床旁屏的 IoT 数据（输液看板/告警提示等）由本模块后端订阅 M14 `/ws/iot` 主题与 `iot.alarm.*` 事件后经本模块 `/ws/ward` 聚合下发，终端不直订 M14；患者离院（discharged）强制解绑终端会话并清空屏端患者数据；终端本地不得持久化患者明细。
4. 布防/撤防、门禁远程开门、婴儿防盗告警联动闭锁、医废交接确认均为安全敏感操作，强制独立权限点+审计留痕；临时撤防必须双人授权+时限，超时自动恢复布防。
5. 禁止跨模块读表：护理级别/责任护士调 M05、费用清单调 M13、报告调 M07/M08、床位与就诊调 M04、遥测与告警调 M14；对外仅暴露 API 与事件。

## 3. 方案推导（关键设计点选型）

### 3.1 模块定位与设备数据边界：全自建直连 vs 全部塞入 M14 vs "感知数据经 M14、业务终端归本模块"双轨（选定）

| 方案 | 说明 | 评估 |
| --- | --- | --- |
| 全自建直连 | 本模块直连输液传感器/标签/冰箱/呼叫主机等全部病房设备 | 与 M14 能力全面重复（接入/绑定/遥测/告警），违背总 Spec 4.5 数据链路与"禁止私建设备通道"的既定架构；告警判定两处维护必然漂移 |
| 全部塞入 M14 | 呼叫状态机、床旁屏内容聚合等业务编排也由 M14 承载 | M14 是设备物联底座（总 Spec：接入/遥测/告警/联动/命令），呼叫路由与内容聚合是纯业务逻辑；床旁屏在总 Spec 5.1 #15 已定性为"调平台 API 的业务终端，非遥测设备"；塞入会使 IoT 底座演变为业务模块，边界崩塌 |
| **感知数据经 M14 + 业务终端归本模块（选定）** | 感知型设备（传感器/标签/探头/按钮/称重终端/呼叫主机与门禁的事件侧）一律经 M14 管道接入与事件发布，阈值判定与告警闭环全部复用 M14；业务终端（床旁屏/门口屏/床头卡/走廊屏/护士站主机界面/移动端）作为应用终端直连本模块 API 与 WebSocket；本模块的场景联动通过配置 M14 联动规则（动作=呼叫转发/门禁联动/发送通知）实现，联动执行引擎在 M14 | 与任务定位一致（业务应用层）；与 M05 方案 3.5"IoT 主题复用 M14、业务域自建"的既定分域同构；三方边界清晰：**M14=数据与判定底座，M05=护理业务权威，M16=病房场景编排与终端编排**；呼叫域归 M16（见 3.2），补齐 M05 大屏"呼叫转发聚合"的事件源 |

三方边界表（统一审查对照基准）：设备接入/绑定判定/遥测/告警判定与闭环/命令下发=M14；护理任务与执行/体征落卡权威/大屏护理域聚合=M05；呼叫域状态权威/病房终端（屏类/床头卡/报警播报）/布防与门禁/冷链与医废合规台账/定位应用=本模块。

**结论**：双轨切分（方案三）。呼叫信令经 M14 `iot.call.triggered` 事件上行、门禁通行经 `iot.access.passed` 事件上行、婴儿防盗告警经 `iot.alarm.triggered` 透传（见第 12 节偏差 1 v1.1 落地口径），屏类业务终端直连本模块。

### 3.2 呼叫域模型：归 M05 延伸 vs 纯外购厂商系统对接 vs M16 独立呼叫域+病区路由配置（选定）

| 方案 | 说明 | 评估 |
| --- | --- | --- |
| 呼叫域归 M05 | 呼叫作为护理任务的一种触发源在 M05 建模 | M05 Spec 已显式声明"呼叫对讲硬件接入与接听流程归 M16，本模块只在大屏聚合展示"；呼叫是患者服务通道（含非护理类请求如缴费协助），塞入护理域会混淆患者服务与护理作业 |
| 纯外购对接 | 呼叫对讲整体外购厂商系统，平台只转发其事件 | 丢失呼叫状态链（应答/转接/完成/升级无从治理）、无法做呼叫→护理任务转换与响应时长统计（评级与质控指标）；厂商锁定 |
| **M16 独立呼叫域+病区路由配置（选定）** | ward_call 呼叫记录+状态机（呼叫→已应答→进行中→已完成/已取消，未应答可转接）；路由规则表按"呼叫类型×时段"配置目标链（护士站主机→责任护士手环/PDA→值班分机，分时段转移对齐调研依据 4）；应答多端（主机接听/移动端应答回传/床旁屏对讲）；超时未应答走动作式升级（对齐 M04 会诊/M14 告警/M05 任务逾期同款设计）；呼叫→护理任务转换按病区配置：默认仅紧急类（卫生间紧急/跌倒求助）自动生成 M05 护理任务留痕，服务类呼叫（换液/如厕协助）仅呼叫闭环，病区可开启"应答自动建任务" | 呼叫域有单一权威与完整状态链；路由/升级/任务转换全部配置化不写死；与 M05 大屏聚合契约衔接（M05 订阅 ward.call.*）；语音对讲流在呼叫子网内端到端（分机↔主机/移动终端，IP 全双工，调研依据 4），平台只承接信令与状态事件，不中转音频、不成为语音瓶颈 |

**结论**：M16 独立呼叫域 + 类型×时段路由配置 + 动作式超时升级 + 任务转换按病区配置（默认仅紧急类转任务）。输液告急的"呼叫联动"（FU-M16-01）落为系统级呼叫记录（类型 INFUSION，source_ref=告警号），经 M14 联动规则触发进入同一呼叫状态链；护理任务升级路径维持 M05 已定契约（告警挂执行单升级），本模块不重复建任务。

### 3.3 床旁屏内容架构：终端直连各模块 vs M16 后端统一聚合 vs 内容复制下沉终端

| 方案 | 说明 | 评估 |
| --- | --- | --- |
| 终端直连各业务模块 | 床旁屏分别调 M13 费用、M07/M08 报告、M05 护理、M04 住院 API 自行拼装 | 终端持有跨模块令牌，鉴权与数据范围失控；模块边界被终端穿透（新增终端形态=全模块改造）；患者数据散落终端缓存，隐私风险不可控 |
| 内容复制下沉 | 各模块数据推送至终端本地库，离线可用 | 患者明细落终端本地持久化，违反隐私红线 3；数据一致性无法保证 |
| **M16 后端统一聚合（选定）** | 屏端唯一数据入口=本模块聚合 API（按"终端+当前绑定患者"维度出内容包：费用区调 M13 一日清单/押金、报告区调 M07/M08 已发布报告、护理区调 M05/M04 摘要、宣教区读本模块宣教库）+ 自建 WebSocket 推送刷新指令；患者凭据绑定（腕带扫码/住院号验证）建立屏端会话；刷新事件驱动（billing.deposit.changed 欠费提醒、报告发布事件、inpatient.* 床位患者变更）；离院强制解绑清屏 | 与联新生产方案"终端深度联动+统一消息"同构（调研依据 2）；权限过滤与脱敏在服务端单点完成；离院清屏可强制执行；聚合 API 缓存兜底屏端体验 |

**结论**：后端统一聚合 + 患者凭据会话 + 事件驱动刷新 + 离院强制解绑。订餐边界：治疗膳食（医嘱驱动）权威在 M04（diet 类）与 M13 计价；床旁自选订餐单为本模块需求采集与状态跟踪台账，金额计价与支付一律调 M13，外部营养膳食系统对接经 M20 预留通道（对齐 M04 膳食分发映射）。

### 3.4 婴儿防盗布防模型：常布防+白名单通行 vs 显式布防/撤防状态机+授权撤防（选定）

| 方案 | 说明 | 评估 |
| --- | --- | --- |
| 常布防+白名单 | 出口常年布防，授权携带（母亲/护士）白名单放行 | 母亲与婴儿标签绑定复杂且误报高（母婴同出是常态）；白名单维护成本高 |
| 仅告警不联动门禁 | 出口只报警不闭锁 | 告警到人控之间存在响应窗口，丢失"第一时间拦截"能力（生产方案均联动门禁/声光，调研依据 5） |
| **显式布防/撤防状态机+授权撤防（选定）** | baby_guard_config 按婴儿建档：产科病区婴儿入科（M04 admitted 事件）→绑定标签→激活布防（ARMED）；出院（discharged）→强制撤防（双人授权+标签回收登记）归档（CLOSED）；护理操作/外出检查走临时撤防（双人授权+时限，超时自动恢复布防）；布防期间出口监视器事件（经 M14 设备事件）→ 告警多端推送（护士站/责任护士手环/安保与消控经 M01）+ 联动门禁闭锁（承接 M14 联动动作"门禁联动"）+ 视频复核接口位（外部视频平台经 M20 预留） | 与生产实现"非解除状态接近出口即报警"语义一致（调研依据 5）；临时撤防双人授权+时限杜绝"撤防忘恢复"；布防/撤防全程留痕满足产科安全管理审计；母婴匹配标签（母亲标签关联）作为防抱错辅助信息 |

**产科业务联动边界**：婴儿在院身份权威=M02（新生儿临时档案，关联母亲档案）+M04（产科住院就诊、入科/出院事件）；本模块订阅 M04 产科病区婴儿 visit 事件驱动布防/撤防，不建婴儿身份档案（与 M03 无直接集成点，M03 为门诊服务无产科条目，详见第 12 节偏差 2）。

### 3.5 RTLS 定位选型与冷链台账分工

**RTLS 分层混合选型**：全院骨干 BLE（RSSI 1-3 米，覆盖资产查找/人员区域定位/手环定位，成本为 UWB 的 1/3~1/5，调研依据 6）；高价值精确定位局部 UWB（婴儿防盗追踪、需要床位级判定的场景，10-30 厘米）；出入口管控用触发式识别（出口监视器/区域信标，事件判定在设备侧而非平台软围栏）。平台侧不做高频坐标实时围栏判定（守红线 1）：患者防走失以"区域边界信标触发事件"为主，软围栏（基于 M14 位置查询的准实时扫描判定）作为 P2 场景化消费预留。位置轨迹存储沿用 M14 遥测策略（位置类指标按指标级保留 30 天，对齐总 Spec 5.1 #11），本模块 rtls_position_cache 只存各标签最新位置与围栏状态，轨迹回放调 M14 查询接口。

**冷链台账与告警分工**：温度遥测、超标/断电/门磁告警的判定与闭环全部在 M14（阈值规则+双通道兜底已定）；本模块只建合规台账——设备档案（含 GSP 验证到期提醒）、温度曲线存证日报（调 M14 时序查询生成快照归档对象存储长期保存）、每日≥2 次人工巡检记录（对齐疫苗规范 2017，逾期经延迟队列提醒）、告警处置记录（引用告警号：库存应急转移/评估结论/销毁建议）、偏差评估记录（短时开门/断电偏差，对齐 CDC 评估口径）。备选"台账也放 M14"被否：温度曲线存证是医疗质量合规档案而非设备运维数据，与设备档案/巡检/处置强关联，放 M14 会把合规台账混入物联底座。

## 5. 状态机与业务流程

- **ward_call**：`CREATED（呼叫中，已按路由链通知）→ ANSWERED（已应答，任一路由端接听）→ IN_PROGRESS（服务进行中，可选节点）→ COMPLETED（已完成，终态，必填处理结果摘要）`；侧支：`CREATED → TRANSFERRED（已转接：未应答转至其他主机/值班，等待被转方应答）→ ANSWERED → …`；`CREATED/TRANSFERRED → CANCELLED（已取消：呼叫方取消、同床位新呼叫合并旧呼叫、重复呼叫合并，终态）`；进行中对讲转移不改状态，仅追加路由日志；`CREATED` 停留超 escalate_after_secs 触发**升级动作**（escalation_count 递增+走廊屏强提醒+门灯长亮+护士长端重复通知，状态不变，仍可被应答）——动作式升级，对齐 M04/M14/M05 既定设计。
- **baby_guard_config**：`ARMED（布防中）⇄ DISARMED（已撤防：必填原因+双人授权；临时撤防带 auto_rearm_at，到期经延迟队列自动回 ARMED）`；`DISARMED（原因=出院）→ CLOSED（已归档，终态：标签回收登记完成）`；布防期间出口/拆卸/心跳丢失告警不改变布防状态，仅触发告警联动。
- **medical_waste_record**：`WEIGHED（称重登记完成，袋码生成）→ IN_TRANSIT（交接中：科室双人扫码确认、收集员转运）→ RECEIVED（已接收：暂存入库/处置单位交接确认，终态）`；侧支：`WEIGHED → CANCELLED（作废重称，必填原因）`；IN_TRANSIT 超时未接收经延迟队列提醒（不改状态）。
- **bedside_terminal 会话**（非设备状态，患者会话维度）：`UNBOUND（未绑定/已解绑默认页）→ BOUND（患者凭据验证绑定）→ UNBOUND（离院事件或护士解除，强制清屏）`。

主流程时序：
1. **患者呼叫**：患者按床头分机呼叫键 → 分机信令经呼叫子网上行（M14 发布 `iot.call.triggered`，本模块订阅）→ 本模块按 ward_call_routing_rule 匹配（类型×时段）建 ward_call（CREATED）并发布 `ward.call.created` → 多端扇出：护士站主机/大屏（`/ws/ward` 呼叫主题+M05 聚合）、责任护士手环与 PDA（经 M01 通知通道）、走廊屏与门灯（终端指令）→ 任一端应答（主机接听或移动端调应答 API）→ ANSWERED（发 `ward.call.answered`，走廊屏/门灯复位）→ 床旁服务完成标记 → COMPLETED（发 `ward.call.completed`）；紧急类呼叫按路由配置自动生成 M05 护理任务（调 M05 任务创建接口）。
2. **呼叫超时升级**：CREATED 停留超阈值 → 延迟队列触发升级动作（重复通知+升级目标）→ 未应答持续升级直至被应答。
3. **输液逐级告警播报（FU-M16-01）**：输液传感器余量遥测 → M14 告警引擎按 15/10/5ml 三档规则触发 `iot.alarm.triggered` → M14 联动规则（动作=呼叫转发/播报）调本模块播报接口 → 分级动作：15ml 看板黄色+走廊屏提示；10ml 看板橙色+床头灯闪+床旁屏本地提示；5ml 报警终端语音播报+系统级呼叫记录（INFUSION，走呼叫状态链可应答/完成）→ 同时 M05 侧按其既定契约对在途执行单做升级动作（本模块不建护理任务）→ 拔针（`nursing.infusion.completed`）后看板复位、未闭环播报自动关闭。
4. **床旁屏内容生命周期**：装机激活码绑定 → 患者入科事件驱动屏端显示绑定引导 → 腕带扫码/住院号验证建立会话（BOUND）→ 内容包按区聚合（费用调 M13、报告调 M07/M08、护理摘要调 M05/M04、宣教读本模块库）→ 刷新事件（欠费/新报告/床位变更）经 WebSocket 推送 → 出院事件（discharged）强制 UNBOUND 清屏复位默认页。
5. **婴儿布防/告警**：产科婴儿入科 → 待绑定提醒 → 护士绑定标签激活布防（ARMED）→ 出口监视器感知布防标签接近/标签拆卸/心跳丢失（经 M14 `iot.alarm.triggered` 透传）→ 发布 `ward.baby-guard.alarmed` → 多端推送（护士站/手环/安保/消控经 M01）+ 联动门禁闭锁（承接 M14"门禁联动"动作）→ 人工现场处置后解除 → 出院双人授权撤防+标签回收 → CLOSED 归档。
6. **冷链超标处置（FU-M16-07）**：温度遥测 → M14 阈值/断电/门磁告警（双通道兜底）→ 本模块订阅告警生成处置待办 → 处置（双人：转移库存/评估/销毁建议）落 cold_chain_record → 处置完成发布 `ward.cold-chain.alert-archived` → 每日两次人工巡检记录+温度曲线存证日报归档。
7. **医废交接**：科室打包称重（称重终端重量取 M14 遥测最新值或移动蓝牙秤）→ 扫袋码建 WEIGHED 记录 → 收集员与科室双人扫码交接（IN_TRANSIT）→ 暂存入库/转运交接扫码确认（RECEIVED）→ 重量与交接统计；区域电子联单上报经 M20 通道（预留）。

## 8. 集成点

- **M01**：认证与 RBAC+数据范围（病区隔离；撤防/远程开门/布防/内容发布/终端管理独立权限点）；通知中心（呼叫与告警多端推送[手环/PDA/短信]、巡检逾期、临时撤防到期、婴儿告警安保/消控通道）；审计切面（全敏感操作留痕）；参数与字典广播订阅；打印（医废交接单/床头卡应急打印模板）。
- **M02**：patient_id 关联一切患者数据；标识解析（腕带/住院号屏端验证）；脱敏规则统一生效（红线 3）；`patient.merged`/`patient.health-summary.updated` 订阅；床旁展示授权对齐其隐私授权体系。
- **M04**：visit_id 引用；床位主数据与占用查询；订阅 admitted/transferred/discharge-requested/discharged/bed.changed 驱动 ward_bed_view、屏内容、婴儿布防/离院解绑；主管医生与医嘱摘要查询（床头卡/床旁屏展示）。
- **M05（护理边界，双向对齐其 Spec 第 7/8 节）**：① 呼叫域归本模块，M05 订阅 `ward.call.*` 仅做大屏转发聚合（其非职责声明一致）；② 紧急呼叫转任务调其 `POST /tasks`，任务状态权威在 M05，呼叫完成不强制任务完成、任务完成不回写呼叫（两态解耦，各自闭环留痕）；③ 输液分工：告急→执行单升级动作维持其已定契约（本模块播报不建任务），在途输注查询调其接口做看板聚合；④ 体征落卡权威在其（FU-M05-02），本模块只做采集编排与视图；⑤ 护理级别/责任护士数据经其查询接口供床头卡与路由（责任护士手环定向推送）。
- **M13**：一日清单/费用查询/押金余额/预计价/支付（床边自助缴费与订餐支付转调其能力）；订阅 `billing.deposit.changed` 刷新床旁费用区；本模块不做任何计价与资金。
- **M07/M08**：已发布报告查询（床旁屏报告区，只读展示）；报告发布事件订阅（新报告提示）。
- **M14（IoT 底座，双向对齐其 Spec）**：① 感知设备数据与事件一律经其管道（遥测/告警/呼叫与门禁信令事件/绑定，订阅 `iot.call.triggered`/`iot.access.passed`/`iot.alarm.*`）；② 告警判定与闭环全部复用其告警引擎（本模块仅提供病区配置向导）；③ 联动规则：本模块场景联动（输液播报/离床转呼叫/门禁联动）配置为其联动规则动作（"呼叫转发/门禁联动/发送通知"），承接其调用；④ 命令下发：屏类终端远程管理指令经其命令通道（白名单安全级）；⑤ WebSocket：IoT 域主题复用（方案 3.1）；⑥ 绑定查询（一体机/标签/屏与患者床位归属）。其 Spec 已预留"转发 M16 呼叫/预留 M16 门禁联动"动作（FU-M14-10），本模块为承接方。
- **M15**：冷链设备与定位标签关联其资产号（FU-M15-01 台账引用）；资产位置与利用率数据供其效益分析；其已订阅本模块 `ward.cold-chain.alert-archived`（设备可靠性记录用途，M15 v1.1 已登记）。
- **M19**：呼叫响应时长、医废重量与交接、环境达标率、满意度统计、输液播报量等取数 API（只读）。
- **M20**：事件信封/交换机/队列治理、幂等构件、延迟队列（`delay.call-escalate` 呼叫升级、`delay.baby-guard-rearm` 复布防、`delay.cold-chain-inspection` 巡检逾期、`delay.waste-handover` 医废超时）、出站通道（外部营养膳食系统/区域固废平台电子联单/视频复核平台均预留经 M20 出站，本期不对接具体对端）；本模块全部事件先登记 event_registry。
- **外部系统（均预留）**：营养膳食配送系统（订餐履约）、区域固体废物管理平台（电子联单）、视频监控平台（婴儿告警视频复核）——对接位经 M20 通道，本期只留接口位与引用字段。

## 9. 非功能与安全

- 性能：呼叫事件端到端（按钮→全部路由端提示）P95 < 1s（呼叫为患者安全通道，对齐生产呼叫系统秒级响应实践）；婴儿防盗出口告警端到端 ≤2s；输液告警播报端到端 ≤2s（复用 M14 告警时延 P95 < 2s 基线）；床旁屏内容包聚合 P95 < 500ms（ward_bed_view 与费用/报告摘要缓存兜底）；看板与主题刷新 ≤2s（总 Spec 8）。
- 可用性：呼叫对讲与婴儿防盗 7×24；**呼叫降级保障**：平台/网络故障时呼叫主机与分机本地呼叫对讲能力不受影响（子网直通，"折网不断呼"，调研依据 2），平台恢复后状态事件按序补传；M14/M13/M07/M08 不可用时对应内容区降级提示（费用/报告区显式"暂不可用"），呼叫与告警通道独立不受牵连。
- 一致性：床位患者视图以 M04 事件为驱动、每日对账兜底；呼叫状态迁移经状态机服务并留迁移日志；事件发布走 outbox（M20 治理约定）；补传的状态事件以 call_no+动作幂等。
- 审计：布防/撤防（含双人授权人与原因）、门禁远程开门与授权变更、医废交接各环节确认、床旁屏会话绑定与解除、宣教发布、终端管理指令全量审计（M01 切面）；婴儿告警处置全过程留痕。
- 权限与隐私：病区数据范围隔离（跨病区呼叫/看板/告警 403）；床旁屏/床头卡输出强制过 M02 脱敏规则，出院强制清屏；床头卡公示字段集经隐私配置约束；人脸介质模板采集单独同意留痕（个保法）；屏端会话与床位强绑定（跨床位内容包拒绝）；日志与事件载荷患者敏感字段脱敏。
- 合规映射：等保三级（审计/TLS/访问控制）；个保法（敏感个人信息单独同意、最小必要展示）；WS/T 840—2025（床头卡每班核对支撑）；疫苗储存和运输管理规范 2017（自动监测+每日两次人工记录，调研依据 7）；医疗废物管理条例第十二条（登记要素与 3 年留存）；医药冷链四类温度口径（调研依据 7）。
- 数据留存：呼叫记录与路由日志≥3 年（呼叫质量与纠纷追溯）；医废台账≥3 年（条例）；冷链台账与处置记录在线≥3 年后归档（温度曲线存证按用途参数化长期保存）；通行记录≥1 年；宣教内容版本留痕。

## 10. 测试要点

- 正常：患者呼叫全链（分机→路由链多端提示→主机应答→完成→事件齐发→M05 大屏可见）；夜班分时段转移值班主机后应答路径正确；紧急呼叫自动生成 M05 任务；输液 15/10/5ml 逐级播报与 5ml 系统级呼叫、拔针复位；床旁屏绑定→内容包各区取数正确→欠费/新报告事件刷新→出院强制清屏；婴儿入科布防→出口告警多端+门禁闭锁→临时撤防到时自动复布防→出院双人撤防归档；冷链超标→告警→双人处置归档→巡检逾期提醒→温度曲线日报存证；医废称重→双人交接→接收→统计。
- 边界：未应答转接后由被转方应答（TRANSFERRED→ANSWERED）与进行中对讲转移不改状态；同床位连续呼叫合并旧呼叫（CANCELLED）；升级动作在应答后停止；临时撤防恰在到期瞬间重新出门的场景；温度恰在阈值边界的告警抖动由 M14 持续时间+恢复带防护（本模块只消费不重复告警）；访客授权过期瞬间通行被拒；医废作废重称后旧袋码失效；转床瞬间床旁屏内容包按新床位患者出数、旧患者会话失效。
- 异常：呼叫子网与平台断连时本地呼叫可用地重建后事件补传不重复（call_no+动作幂等）；M14 事件重复投递（iot.call.triggered/iot.access.passed/iot.alarm.*）不产生重复呼叫/重复通行台账/重复播报/重复处置待办；M05 任务接口不可用时紧急呼叫转任务进入重试且呼叫状态不受阻塞；M13 不可用床旁费用区降级提示；婴儿标签心跳丢失触发离线告警（M14 规则）；称重终端断流经 `iot.telemetry.anomaly` 提示；屏端激活码重放被拒。
- 安全：跨病区订阅呼叫/告警主题 403 且留审计；无撤防权限撤防被拒；单人操作临时撤防被拒；远程开门无独立权限被拒且审计；床旁屏跨床位请求内容包被拒；患者出院后旧会话请求返回未绑定；日志与事件载荷患者敏感字段脱敏抽验；人脸模板未获单独同意不可启用。

1. **事件型设备业务事件上行通道（v1.1 按统一审查裁决落地）**：泛化 `iot.device.event` 被统一审查否决；M14 v1.1 已登记具体事件并由本模块订阅——呼叫信令上行 `iot.call.triggered`（路由建 ward_call）、门禁通行结果 `iot.access.passed`（落通行台账）；婴儿防盗出口/拆卸/心跳丢失告警经 `iot.alarm.triggered` 透传（M14 设备报警规则），门禁闭锁/输液播报由 M14 联动动作（"门禁联动"/"呼叫转发"）调本模块接口承接；医废称重走遥测最新值+扫袋码建档。呼叫=事件订阅、门禁闭锁/输液播报=M14 联动动作的二分口径成立。
2. **婴儿防盗的产科业务联动对象**：任务提示"M03 婴儿登记边界"，经核对总 Spec 与各上游 Spec，M03 为门诊服务且无产科条目；新生儿身份权威在 M02（新生儿临时档案、可关联母亲档案，FU-M02-01）与 M04（产科住院就诊、入科/出院事件）。本 Spec 按 M02/M04 口径对齐（M16 与 M03 无直接集成点），如产科婴儿登记另有归属请统一审查裁决。
3. **FU-M16-01"呼叫联动"细化**：输液逐级告警的呼叫联动落为——阈值判定与告警在 M14、联动规则动作触发本模块分级播报、5ml 紧急档生成系统级呼叫记录（INFUSION）走呼叫状态链；护理任务升级路径维持 M05 已定契约（告警挂执行单升级），本模块不重复生成护理任务，避免双任务风暴（与 M05 方案 3.4"任务风暴"论证一致）。
4. **FU-M16-02 分工澄清**：总 Spec 条目"数据自动入护理记录单（双通道校验）"的落卡权威与双通道仲裁在 M05（FU-M05-02 已定三源归一与质量闸门），本模块承载一体机/床垫的病区采集编排、测量队列与监测视图，不做落卡与二次判定。
5. **FU-M16-04 订餐口径**：治疗膳食（医嘱驱动）权威在 M04（diet 类）与 M13 计价；床旁自选订餐单为本模块需求采集与状态台账，资金与计价一律调 M13，外部营养膳食系统对接经 M20 预留（对齐 M04 膳食分发映射"外部营养膳食系统对接经 M20 预留接口位"）。

其余无偏差：FU 条目编号与优先级、设备矩阵 15 类中智慧病房相关设备的接入方式（5.1 #3/6/8/9/10/11/12/13/14/15）、模块定位（业务应用层）、阈值判定归 M14、IoT 主题复用等均与总 Spec 及上游 Spec 一致。
