# 模块 Spec 规范（所有模块文档必须遵守）

本文档定义 `docs/specs/modules/` 下所有模块 Spec 的统一结构、命名与跨模块约定，用于保证 20 份模块 Spec 之间不产生冲突。上游文档：`docs/specs/00-master-spec.md`（总 Spec v1.1）。

## 1. 文档命名与编号

- 文件名：`MM-<name>.md`（如 `01-system.md`、`14-iot.md`），MM 与总 Spec 模块号一致。
- 功能点编号沿用总 Spec：`FU-M<模块号>-<序号>`；模块 Spec 中不得新增/删除 FU 条目，只能细化。如细化中发现总 Spec 功能点需调整，在 Spec「与总 Spec 的偏差」一节记录，由统一审查裁决。

## 2. 统一章节结构（每份模块 Spec 必须包含，顺序固定）

文档头（模块号/名称/版本/状态/上游依赖/下游被依赖）以表格形式置于标题行之后，不计节号；正文固定为第 1-12 节：

1. 模块定位与边界（职责、非职责、模块红线）
2. 调研依据（真实生产实现来源，带 URL）
3. 方案推导（关键设计点的备选方案对比与选型理由，≥1 个关键点）
4. 领域模型（核心实体、关系、关键字段、表设计要点）
5. 状态机与业务流程（核心对象状态机 + 主流程时序）
6. 功能实现设计（逐 FU 条目细化实现方案）
7. 对外接口（REST API 清单 + MQ 事件清单 + WebSocket 主题）
8. 集成点（依赖谁、被谁依赖、与 M14/M20 的关系）
9. 非功能与安全（性能、审计、权限、合规映射）
10. 测试要点（正常/边界/异常场景，对应验收标准）
11. 自审记录（按第 4 节清单逐项结论）
12. 与总 Spec 的偏差（无则写“无”）

## 3. 跨模块统一约定（冲突预防基线）

- **数据库**：单 PostgreSQL 16 实例，每模块独立 schema（`system`/`patient`/`iot`/…），schema 名 = Maven 模块名；跨模块禁止直接读表，只能经 API/事件。
- **金额**：一律 `BIGINT` 分值制（单位分；分↔元换算集中在应用层 MoneyUtil，JSON 序列化字符串承载）；服务端计算。
- **主键**：业务表用 `BIGINT` 雪花 ID（分布式预留）；关联表用复合唯一约束表达业务键。
- **审计字段**：所有业务表统一 `created_by/created_at/updated_by/updated_at/deleted(逻辑删)`。
- **时间**：`TIMESTAMPTZ`，一律服务器时间（禁止前端传入业务时间）。
- **MQ 事件命名**：`<模块>.<实体>.<动作>`，如 `order.created`、`lab.critical-value.notified`；事件载荷必须含 `eventId(UUID)/occurredAt/producer` 信封字段；所有消费必须幂等（以 eventId 去重，`integration.received_event` 表统一记录）。
- **交换机**：`fy.topic`（领域事件 Topic 交换机）、`fy.dlx`（死信）、`fy.delay`（TTL+DLX 延迟队列，队列名 `delay.<业务>`）；队列命名 `q.<消费者模块>.<事件>`。
- **REST 风格**：`/api/v1/<module>/<resource>`；响应统一 `{code, message, data, traceId}`。
- **字典**：国家标准字典由 M01 统一维护并经 `fy.topic` 广播，M20 负责分发治理（订阅登记/对账/补偿重发），业务模块只存 `code` 引用，禁止自建国标字典副本。
- **状态机**：状态字段用 `VARCHAR` 常量（非魔法数字），状态迁移必须经状态机服务校验并留迁移日志。
- **患者关联**：一切临床数据引用 `patient_id`（M02 EMPI 主键）+ `visit_id`（就诊/住院唯一标识，由 M03/M04 签发）。
- **优先级标注**：细化条目沿用总 Spec P0/P1/P2。
- **依赖方向判定口径**：同步 API 调用方=依赖方；事件订阅不构成依赖方向。文档头的上游/下游按此口径标注。

## 4. 自审清单（每份 Spec 定稿前逐项检查，结果写入文档「自审记录」）

- [ ] 无 TBD/TODO/占位符；每节内容完整
- [ ] 覆盖总 Spec 中本模块全部 FU 条目，无遗漏、无私增
- [ ] 内部一致：领域模型 ↔ 状态机 ↔ API ↔ 测试要点相互对应
- [ ] 与跨模块约定（第 3 节）无冲突：事件命名、schema、患者关联、字典引用
- [ ] 依赖方向正确：只依赖上游模块的对外接口，无反向依赖、无跨模块读表
- [ ] 方案推导有备选对比，选型有依据（引用调研来源）
- [ ] 无代码级实现（不出现类名/方法体/SQL DDL 全文；表设计仅描述到"表-关键字段-约束"粒度）
- [ ] 歧义消除：每个需求只有一种解释
- [ ] 中文注释与术语一致（医嘱/处方/申请单等用词与总 Spec 一致）
