## 一、修复清单（≥80 且无争议，4 项）

### PERF-01（原 BE-REFUND-CHAIN，置信 88，确认；吸收 P1-01/P1-04/P3-05/A2-01/A2-02）
- **问题**：退费链 apply/execute 全量拉取与循环重复查询。`RefundServiceImpl.apply`(:209) 逐费用行调 `refundedFen`(:616-630)，每次把全部 PENDING_* 在途退费单整行拉入内存仅取 id；`decidedRefundedFen`(:643-653) 每次把全部 APPROVED/EXECUTED 退费单（EXECUTED 终态单调无界增长）整行实体拉入内存仅取 id，且 status 无前导索引（V603 仅 idx_refund_settlement(settlement_id,status)）顺序扫描；`execute`(:485-491) 每 link 串 selectById + decidedRefundedFen（循环内不变集合重复全量拉取）+ updateById；apply(:250-258) 逐行 insert fee_link。N 行明细退费单 → 数倍 N 条查询 + N 次全表实体拉取，资金热路径随运营年限量级劣化。
- **证据**：backend/fuyun-billing/src/main/java/com/fuyun/billing/service/impl/RefundServiceImpl.java:209/250-258/485-491/616-630/643-653；db/migration/billing/V603__create_settlement_and_refund.sql:60。
- **修复方案（行为保持）**：①decidedRefundedFen/refundedFen 改 SQL 聚合下推——新增 mapper 聚合查询（refund_fee_link JOIN refund_request 按 status 过滤 SUM(refund_amount)，及在途单 EXISTS 语义），等额守卫计算结果与现实现完全一致；②apply 内 refundedFen 对同批 fee 的不变集合一次装载复用；③execute 循环内 link 批量预载（selectBatchIds）+ decidedRefundedFen 结果循环外一次复用；④apply 逐行 insert link 改 saveBatch。测试：金额边界对照断言（部分退/全额退/在途排斥/免审直退路径结果与旧实现一致）+ 并发语义不回归。
- **影响面**：fuyun-billing RefundServiceImpl + RefundRequestMapper（新增聚合 SQL）；对外契约零变更。
- **复杂度改善**：时间——查询次数 O(明细数×全表行数) 顺序扫描 → 每批常数条聚合查询（N4 修订注：refund_fee_link 现无 fee_id 前导索引——该缺口为观察项 BE-P1-05（78 分）未入修复清单，聚合 JOIN 当前为顺序扫描，但相较基线「逐明细全量实体拉取」仍为严格改善；若 BE-P1-05 后续落地则为索引聚合）；空间——O(全院已决/在途退费单整行实体) 内存驻留 → O(聚合结果行)。

### PERF-02（原 BE-P1-02，置信 80，确认）
- **问题**：vital_sign_record 无 patient_id 前导索引。`VitalSignServiceImpl.listByPatient`(:212-223) 按 patient_id 过滤（工作站 GET /vital-signs?patientId= 与 PDA 患者摘要每次扫码均调用），V803 仅有 (visit_id,*) 与 (ward_id,review_status) 索引，顺序扫描；体征表为全院持续增长高速写入表（P2 IoT 接入后放大）。
- **证据**：backend/fuyun-nursing/src/main/resources/db/migration/nursing/V803__create_vital_sign.sql:40-42；VitalSignServiceImpl.java:212-223。
- **修复方案（行为保持）**：新增增量迁移 `V80x__add idx_vital_sign_patient_time ON nursing.vital_sign_record (patient_id, measured_at)`（不触 A.4.1-3 既有迁移禁改红线）；查询无需改动即受益。测试：迁移可重复执行（Flyway IT）+ listByPatient 行为保持。
- **影响面**：fuyun-nursing 迁移目录；查询计划由顺序扫描 → 索引范围扫描。
- **复杂度改善**：时间——患者维度查询 O(全表) → O(log n + 患者行数)。

### PERF-03（原 BE-P1-03，置信 82，确认）
- **问题**：患者姓名检索前导通配全表扫。`PatientServiceImpl.search`(:156-161) 对姓名关键词生成 `name LIKE '%kw%'`（MP like），V100 idx_patient_name 普通 B-tree 无法服务前导通配，挂号台最高频入口对百万级主档全表扫描 + 全表 COUNT（分页 total）。
- **证据**：backend/fuyun-patient/src/main/java/com/fuyun/patient/service/impl/PatientServiceImpl.java:156-161；V100__create_patient.sql:36-41。
- **修复方案（行为保持）**：新增 pg_trgm 扩展 + GIN 索引（gin (name gin_trgm_ops)）增量迁移，使 '%kw%' 走 trigram 索引；查询语句不变，结果集不变（含空串/单字边界行为）。测试：检索结果对照断言（同关键词返回集与排序一致）+ 迁移 IT（扩展幂等 CREATE EXTENSION IF NOT EXISTS）。
- **影响面**：fuyun-patient 迁移目录；检索路径顺序扫描 → GIN trigram 索引扫描。
- **复杂度改善**：时间——姓名检索 O(全表) → O(索引候选集)。

### ALGO-01（原 BE-PDA-VITALS，置信 80，确认；吸收 P1-08/A2-03）
- **问题**：PDA 患者摘要全量体征取末位。`PdaServiceImpl.patientSummary`(:152-154) 调 `listByPatient(patientId, null, null)` 按患者主索引跨全部住院史无窗口无 LIMIT 全量拉入内存 + 全量 VO 转换，仅为取最后一条作摘要；长期住院/慢性病患者数千行，叠加 PERF-02 缺索引=全表扫+全史传输。
- **证据**：backend/fuyun-nursing/src/main/java/com/fuyun/nursing/service/impl/PdaServiceImpl.java:152-154；VitalSignServiceImpl.java:212-223。
- **修复方案（行为保持）**：VitalSignService 新增 `latestByPatient(patientId)` 点查（ORDER BY measured_at DESC, id DESC LIMIT 1——与升序末位取值语义一致且确定性 tie-break），patientSummary 改用之。测试：构造多条体征（含同刻 tie）断言与旧实现「升序取末位」取值一致。
- **影响面**：fuyun-nursing VitalSignService/Impl + PdaServiceImpl；对外契约零变更。
- **复杂度改善**：时间/空间——O(患者终身体征行数) 全量拉取+转换 → O(1) 单行点查（配合 PERF-02 索引）。
